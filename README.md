# AWS Engineer Onboarding with CloudFormation Git Sync

Repeatable, auditable onboarding of engineers into an AWS account, managed entirely as code.
Every access change is made through Git, deployed by CloudFormation Git sync, capped by
IAM permission boundaries and recorded by CloudTrail.

## Overview

| Engineer     | Group                  | Job policy (AWS managed)  | Permission boundary          |
|--------------|------------------------|---------------------------|------------------------------|
| `s3-user`    | storage-engineers      | `AmazonS3FullAccess`      | `boundary-storage`           |
| `ec2-user-1` | compute-engineers      | `AmazonEC2FullAccess`     | `boundary-compute`           |
| `ec2-user-2` | oncall-observers       | `AmazonEC2ReadOnlyAccess` | `boundary-compute-observer`  |

Key design principles:

- **Least privilege by ceiling.** Effective access is the intersection of identity policies and
  the permission boundary. Even if someone later attaches `AdministratorAccess` to a user or
  group, the boundary still limits what they can do.
- **Groups, not users, carry permissions.** Groups use AWS managed policies only. No inline IAM
  policies are used.
- **No secrets in Git.** First-login passwords are generated by AWS Secrets Manager, and users
  must reset them at first sign-in.
- **Full audit trail.** A multi-region CloudTrail trail (including global IAM events) writes to
  an encrypted, versioned, private S3 bucket with log file validation enabled.
- **GitOps deployment.** Merging to `main` updates the stack through CloudFormation Git sync.

## Architecture

```
GitHub (main) ──► CodeConnections ──► CloudFormation Git sync
                                          │  assumes onward-gitsync-role
                                          ▼
                              Stack: onboarding (templates/onboarding.yaml)
                                          │  built by onward-onboarding-stack-role
        ┌──────────────────┬──────────────┼──────────────────┬──────────────────┐
        ▼                  ▼              ▼                  ▼                  ▼
  Permission          IAM groups      IAM users        Secrets Manager     CloudTrail +
  boundaries                                           (initial passwords)  S3 audit bucket
```

## Prerequisites

- An AWS account and an IAM principal with administrator access
- [AWS CLI v2](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)
  configured for the target account and region
- Access to this GitHub repository, with permission to authorize an AWS connection

## Deployment

### 1. Deploy the bootstrap stack (once)

```bash
aws cloudformation deploy \
  --template-file bootstrap/gitsync-bootstrap.yaml \
  --stack-name onward-gitsync-bootstrap \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation describe-stacks \
  --stack-name onward-gitsync-bootstrap \
  --query 'Stacks[0].Outputs' --output table
```

### 2. Complete the GitHub connection

The connection is created in a `PENDING` state. In the AWS console, go to
**Developer Tools → Settings → Connections**, select `onward-onboarding-repo`,
choose **Update pending connection** and authorize GitHub. AWS requires this step to be done
in the console.

### 3. Create the stack with Git sync

In the AWS console, go to **CloudFormation → Create stack → Sync from Git** and set:

| Setting              | Value                          |
|----------------------|--------------------------------|
| Stack name           | `onward-onboarding`            |
| Repository / branch  | this repository, `main`        |
| Deployment file path | `deployment-file.yaml`         |
| Git sync IAM role    | `onward-gitsync-role`          |
| Stack service role   | `onward-onboarding-stack-role` |

From then on, every merge to `main` that changes the template or the deployment file updates
the stack automatically.

### 4. Deliver initial credentials

Retrieve each first-login password and send it to the engineer through a secure, out-of-band
channel together with the console sign-in URL from the stack outputs:

```bash
aws secretsmanager get-secret-value \
  --secret-id onward/prod/onboarding/s3-user \
  --query SecretString --output text
```

Repeat for `ec2-user-1` and `ec2-user-2`. Users must set a new password at first sign-in.

## Configuration

Parameters are set in [`deployment-file.yaml`](deployment-file.yaml):

| Parameter          | Default | Description                                                                 |
|--------------------|---------|-----------------------------------------------------------------------------|
| `Environment`      | `prod`  | Prefix for resource names (lowercase letters, digits and hyphens).          |
| `CreateAuditTrail` | `true`  | Set to `false` if the account already has an organization or account trail. |

## Verification

[`evidence.sh`](evidence.sh) produces evidence that access is correct. Run it as an
administrator:

```bash
ENV=prod bash evidence.sh
```

It performs five checks:

1. **Day-one access:** simulates each engineer's permissions with the IAM policy simulator.
2. **Stress test:** temporarily attaches `AdministratorAccess` to `ec2-user-2` and its group,
   and shows that the observer boundary still denies creating, starting and terminating instances.
3. **Revert:** removes the temporary `AdministratorAccess` attachments.
4. **Audit:** lists who changed access and when, from CloudTrail event history (`us-east-1`).
5. **Drift check:** confirms each user has the permission boundary defined in Git.

> **Warning:** Step 2 grants administrator rights for a short time. Run the script in a test
> account, or confirm that step 3 completed. If the script stops early, detach the policy
> manually.

## Security considerations

- `onward-onboarding-stack-role` has broad permissions (`iam:*`, `s3:*`, `secretsmanager:*`,
  `cloudtrail:*`). Anyone who can merge to `main` can change IAM in the account. Protect `main`
  with branch protection and required reviews.
- The audit bucket uses `DeletionPolicy: Retain` and is kept when the stack is deleted.
- User names are fixed. Only one environment can be deployed per AWS account.

## Clean up

First disconnect Git sync from the stack (CloudFormation console → stack → **Git sync** →
**Disconnect**), so a later push cannot recreate it. Then delete the stacks:

```bash
aws cloudformation delete-stack --stack-name onward-onboarding
aws cloudformation delete-stack --stack-name onward-gitsync-bootstrap
```

Finally, empty and delete the retained audit bucket.
